# Long-Story Retrieval Benchmark: Test Protocol

Written and committed **before** any data for this benchmark was generated. If anything below changes after the test run, the change and its reason are recorded in the results, never edited in place.

## 1. Questions this benchmark answers

1. **Primary:** On a long story (300 rounds, ~600 turns), how often does the frozen v2 retriever put a chunk that answers a recall question into the 10 chunks that go into the writer's prompt (Recall@10)?
2. How does Recall@10 change as the story grows (snapshots after rounds 100, 200, 300), and does v2 hybrid degrade more slowly than v1 tier search?
3. Which question types fail, and are failures caused by retrieval or by the chunk summary not containing the answer at all?
4. End to end: does the writer's answer agree with the recorded past?

## 2. Methods compared

All methods search the same session's memory chunks. Query rewriting uses the production `translateUserIntent` with the snapshot's world state and its last 3 chat turns.

| Method | Definition |
|---|---|
| **v1 tier search** | Embed the rewritten query (rewrite + entity names); vector search filtered to chunks whose metadata mention any extracted entity; top up with unfiltered vector results to 10. Reimplemented as in `scripts/eval/rank_vectors.ts` (the production code was removed in v2). |
| **BM25 only** | Okapi BM25 (k1 = 1.5, b = 0.75, rank_bm25 IDF) over chunk summaries; query = raw input + rewritten query. |
| **Vector only** | Embed the raw player input; unfiltered vector search. |
| **v2 hybrid (frozen)** | The production retriever at the frozen commit (Section 7). |
| Union ceiling | Top 10 of BM25 only ∪ top 10 of vector only. Reported for reference, not a deployable method. |

## 3. Data

Two stories generated by `generate.ts` with identical settings: same auto-player model and prompt, 12 chapters × 25 rounds = 300 rounds, a forced change of location and objective at every chapter, a follow-up on an earlier entity every 4th round, and one deliberately triggered recurring event per chapter (3 event types, each occurring about 4 times). Snapshots are saved after rounds 100, 200, and 300. The two stories differ only in their setting (`stories.ts`): **dev** is a sci-fi salvage thriller, **test** is a high-fantasy expedition.

- **dev story** and the earlier 100-round **pilot** story: development data. They can be used for any analysis and tuning, as often as needed.
- **test story:** generated at the same time as the dev story, then left untouched until the freeze (Section 6).

The production pipeline that generates both stories is the v2 code at the commit containing this protocol.

## 4. Questions

**Source chunks.**
- **early:** chunks that exist at the round-100 snapshot.
- **late:** chunks created between the round-100 and round-300 snapshots.
- Chunks whose extracted content (original text after `[Content to Extract]`, turn markers removed) has fewer than 40 words are skipped.
- Source chunks are sampled evenly across turn order.

**Generation.** `gpt-4o-mini` writes player-style recall questions. It sees **only the chunk's original text**, never its summary, so questions do not inherit the summary's wording. Per story and per pool (early and late):

| Type | Count | Definition |
|---|---|---|
| detail | 20 | A specific concrete detail from the passage: an object, a phrase someone said, a number, a consequence. Natural player phrasing, not copied sentences. |
| vague | 15 | The same kind of question, but with no proper names; people, places and things are referred to by description ("the old woman at the well", "the thing I pulled from the wreck"). |
| temporal | 10 | Asks about the n-th occurrence of a recurring event type ("the first time Bastian's men ambushed us, ..."). |

**Temporal questions.** Each chunk's original text is tagged by `gpt-4o-mini` with the recurring event types it depicts. Occurrences are ordered by `start_turn`, and the ordinal counts from the start of the story. The question targets the first or second occurrence (early pool) or a later occurrence (late pool), asks about a detail of that occurrence, and its source chunk is that occurrence's chunk.

That gives 90 questions per story (45 early, 45 late). Questions are generated once per story and never regenerated after seeing results.

**Validation.** The labeling judge (below) must confirm that the source passage answers its own question. Questions that fail are dropped; their number is reported.

## 5. Labels (multiple correct chunks)

A question can have several correct chunks: an event split across two chunks, or a repeated detail. Labels come from an LLM judge (`gpt-4o-mini`, temperature 0) that compares each candidate chunk's original text with the **reference passage** (the source chunk) and decides:
- detail and vague: does the candidate contain the answer to the question?
- temporal: does the candidate depict the same occurrence as the reference passage and contain the answer?

**Candidate pool.** The source chunk plus the union of every method's top 10 at every snapshot. Every chunk that can affect Recall@10 for these methods is therefore labeled. On the dev story, the pool also includes the top 30 of BM25 only and vector only, so that new fusion settings can be scored. The correct set at snapshot T is the set of acceptable chunks that exist at T.

**Summary attribution.** The judge also checks whether the source chunk's summary contains the answer. Misses are reported separately for "answer in summary" and "answer only in original text".

## 6. Rules

1. Before the freeze, the only allowed contact with the test story is checking that generation completed (the end of the log, chunk and snapshot counts). Nothing else: no questions, labels, retrieval runs, or reading of chunk text.
2. Development (Section 7) uses only the dev and pilot stories.
3. **Freeze:** the retrieval configuration and code are committed, and the commit hash is recorded in `FREEZE.md` before the test run.
4. The test story is then evaluated **once**: generate questions, label, retrieve at all three snapshots, run the end-to-end check, and report every number in Section 8, whether it looks good or bad.
5. No retrieval or prompt change is evaluated on the test story after this run. If a bug in the **evaluation** code is found afterwards, it may be fixed and the run repeated; the bug and both results are reported. Evaluating any later version requires a new test story.

## 7. Development before the freeze

- Allowed changes: anything in retrieval (fusion method, weights, depth, query inputs).
- **Objective: Recall@10**, not MRR. The writer receives all 10 chunks, re-sorted by turn, so rank inside the top 10 does not matter.
- Tuning data: dev questions at all three snapshots, plus the pilot story's 88 questions (single source chunk as the only correct answer).
- Selection: 4-fold cross-validation grouped by source chunk, repeated 25 times. Among strategies within 0.01 Recall@10 of the best cross-validated score, the one with the fewest tuned parameters wins.
- The writer prompt and everything outside retrieval stay as at the protocol commit.

## 8. Reported results (test story)

- **Primary:** Recall@10 of v2 hybrid at the round-300 snapshot over all valid questions.
- Recall@10 of every method in Section 2, at the round-300 snapshot.
- **Curve:** Recall@10 of every method on the early questions at the round-100, 200 and 300 snapshots (the same questions, with more distractor chunks each time).
- Recall@5; Recall@10 by question type (detail, vague, temporal); misses split by summary attribution.
- **End to end at the round-300 snapshot:** the frozen writer answers each question with the frozen retrieval, and a judge rates the answer against the reference passage as correct, contradicts, or absent.
- **Uncertainty:** 95% percentile bootstrap intervals (10,000 resamples of questions) for Recall@10, and for the paired difference between v2 hybrid and v1 tier search.

## 9. Known limitations

- Two stories, both machine-played. Questions and labels come from LLMs, judged by a single model.
- Recall@10 depends on corpus size: the later snapshots have more chunks, which is the point of the curve, but absolute numbers do not transfer to other story lengths.
- The pilot results (`scripts/eval/out`) were produced before this protocol and are development data only.
